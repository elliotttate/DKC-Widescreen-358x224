# v0.1 live-session audit (2026-08-14)

Audited session: `DKCObjectLifecycleTracer/Sessions/20260814-204150` in the
local v0.230 test installation. Runtime evidence is intentionally not tracked.

This audit explains why the v0.1 anomaly count was not trustworthy and what
v0.2 changed. The emulator and installed plugin were not modified during the
audit.

## Root causes

1. **Non-gameplay WRAM was decoded as gameplay.** DKC reuses the actor arrays,
   `$192B`, level/entrance fields, and camera fields on maps and menus. A
   captured world-map frame had entrance `$00E6` and zero camera bounds, while
   the reused actor bytes happened to decode as repeated Diddy IDs. Those were
   not actor allocations.
2. **The entrance table was read past its end.** In
   `DKC1_Disassembly/DKC1/Routine_Macros_DKC1.asm`, `DATA_BD8000` begins at
   `$BD8000`; the next label is `DATA_BD81CC`. The table is therefore `$1CC`
   bytes, or exactly `$E6` 16-bit entries. Entrance `$E6` is the first invalid
   index. v0.1 read the bytes after the table as a pointer and reported an
   invalid `$0001` object-list pointer.
3. **Actor offsets were labeled as derived slots.** The bank-BD allocators at
   `CODE_BDF3A2` and `CODE_BDF3C3` search raw X indexes
   `$02,$04,...,$1C` and `$1E,$20,...,$32`. Those raw indexes are stored in
   `$192B`; `$15FD,x` stores the source object-record index. v0.1 sampled the
   right two-byte stride but included unused raw index `$00` and labeled
   `index/2` as a slot, obscuring what the game actually stores.
4. **Transient ownership states were called anomalies.** DKC clears actor ID
   and `$15FD` in routines separate from the scanner sites that clear `$192B`.
   A frame can therefore contain a stale bookmark without proving a failed
   spawn. Duplicate references, source/back-reference mismatches, and missing
   type-5 children are useful leads but require scanner/write history. They are
   now non-definitive observations; only impossible odd/out-of-pool bookmark
   values are immediate structural anomalies.
5. **Save-state replays inflated counts.** The differential runner repeatedly
   loaded the same states, moving the frame counter backward. v0.1 did reset
   its in-memory diff state, but its offline report summed all replay timelines
   as though they were one run. The analyzer now assigns trace segments and
   reports unique observation signatures separately from raw starts.
6. **v0.1 reversed actor-pool success and exhaustion.** Clean-ROM bytes at
   `$BDF3A2` branch to `$BDF3B5` when a zero actor ID is found. `$BDF3B1` is
   `STZ $86; SEC; RTS` (exhaustion), while `$BDF3B5` stores X in `$86`, marks
   `$15FD,x` as `$8000`, and returns carry clear (success). The secondary
   equivalents are `$BDF3D2` and `$BDF3D6`. A v0.1 `$BDF3B5/$BDF3D6`
   “exhausted” row is therefore proof that the old label was wrong, not that
   the pool was full. v0.2.1 corrects live labels and normalizes old scanner
   files by PC.

## v0.2 trust boundary

Gameplay object tracing requires both:

- entrance `< $00E6`; and
- nonzero, ordered `$1B23/$1B25` camera bounds.

If either test fails, actor/bookkeeping/object decoding and both optional hot
hooks are suppressed. `current.json` still reports the raw context identifiers,
`objectTracingActive: false`, and the reason, but does not publish false actor
or authored-object data.

Transient observations must persist for three consecutive gameplay frames by
default before an `observation_started` event is emitted. They remain labeled
`definitive: false`; the write and scanner streams are the evidence needed to
decide whether one is a real softlock mechanism.

## Offline validation

- Release build: zero warnings, zero errors against SuperZSNES v0.230 managed
  assemblies and BepInEx 5.
- Model tests: 12/12 pass when given the clean USA v1.0 ROM, including its
  SHA-256 and exact primary/secondary branch, exhaustion, and success opcodes,
  plus raw actor indexes, map gating, bounded
  entrance decode with zero memory reads, object/group decode, lifecycle diffs,
  and anomaly/observation classification.
- Python analyzer compiles with the standard library only and reclassifies all
  v0.1 stale ownership messages in the audited session as observations rather
  than definitive anomalies.
