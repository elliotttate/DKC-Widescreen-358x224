## State 0: Croctopus Chase

The section controller is internally consistent at the attached checkpoint:

- `$1E03=$0201`, `$1E05=$0000` (no pending boundary record),
  `$1E07=$0A`, `$1E0B=$17`, and scanner `$A0=$0A`.
- Records `$0A..$17` are exactly the second type-$09 range in
  `DATA_BDA7BE`.
- `$0A` (`ChompsJr`, authored `$0110,$5660`) and `$0B` (`Croctopus`,
  `$0110,$56AC`) are active. The normal allocation pool has ten free entries.
- `$0C` is the KONG letter O at `$0130,$576B`; zero bookkeeping is expected if
  previously collected.
- The next paired barrel cannons are records `$0D/$0E` at X `$01DE`, followed
  by `$0F/$10` at X `$0202` and the logic-critical `CameraObject` record `$11`
  at `$0218,$5640`.

At the checkpoint itself there is no allocation pressure and no section-range
corruption. The most useful next failure capture is the first frame after
Layer1 X reaches about `$00C0`: at that point the `$0218` camera object first
enters the wide window. If `$192B+$11` stays zero while the camera approaches
it, the camera object was scanned but failed allocation; if `$A0/$1E07/$1E0B`
switch away from `$0A..$17`, the type-$09 controller selected the wrong range.
Those two cases require different fixes.

## State 1: Poison Pond

This state is more suspicious because the wider window is already consuming
additional normal-sprite slots:

- Type-$09 state is `$1E03=$0403`, no pending boundary pointer, scanner range
  `$35..$47`, which matches the final `DATA_BDA584` range.
- The type-$05 parent at record `$35` is active (`$192B+$35=$FF`) and both
  children are present: bookkeeping `$84=$0E`, `$85=$10`.
- The two record-$0F Mincers at X `$0186` are wide-only at Layer1 X `$0052`.
  Both are already allocated (`$192B+$37=$06`, `$192B+$38=$08`). Stock would
  not activate them at this camera position. This costs two of the normal
  pool's six remaining slots.
- Record `$36`, a barrel cannon at `$0140,$6DC4`, has zero bookkeeping despite
  being in range. That can be valid if it was already used, so a successful
  run from the same checkpoint is needed as the oracle.
- The next hard logic dependency is record `$3D`, a `CameraObject` at
  `$0350,$6DE0`. Later range `$46` is another `CameraObject` at
  `$0750,$6E30`.

The leading hypothesis is pool/timing pressure, not a missing compare patch:
wide-only ordinary actors are allocated before an upcoming barrel/camera
record. The current type-$05 retry does not prioritize type-$02 camera objects
or type-$01 barrel cannons. A paired good/bad trace should log allocation
failures in `CODE_BDF3A2`, requested record index/type, `$A0`, `$192B`, and the
normal pool. If a camera object loses the last slot, the robust fix is a
logic-critical reservation or retry policy, not another blanket margin.

## State 2: Gang-Plank Galleon

The bank-$BD loader is healthy here:

- record `$00` (`MinigameController`, authored `$0100,$0127`) is active;
- record `$01` (sprite `$75`, authored `$0002,$0100`) is active; and
- K. Rool (`$70`) has been created by the controller. The normal pool has nine
  free entries.

The stronger defect candidate is outside the object loader. K. Rool's movement
uses camera bounds as **logical arena edges** in `CODE_B6E15F`:

```asm
LDA XPos
CMP $1B23
...
CMP $1B25
...
LDA $1B25
ADC #$0100
```

The wide camera patch changes the attached fight's bounds from their logical
stock form to `$0038..$00C8`. Without compensation, K. Rool is constrained to
`$0038..$01C8` rather than the stock arena. At the state he is already X
`$01D0`, substate `$0F`, eight pixels beyond that widened right edge. This is
an exact, scene-specific way for a camera-only change to alter boss AI.

There is a second uncompensated read in `CODE_B6E826` (`$B6E826`):

```asm
LDA Layer1X
SEC
SBC $1B23
CMP #$0080
```

Raising `$1B23` by `$38` delays the fight-state advance by 56 world pixels.
The checkpoint has Layer1 X `$00BC`, barely past the new `$00B8` threshold.

The first boss-specific experiment should reconstruct stock logical bounds
inside `CODE_B6E15F` and the stock world threshold inside `CODE_B6E826`, while
leaving camera/render bounds wide. This is safer than exempting the whole boss
room from widescreen and directly separates presentation bounds from gameplay
bounds.

### 16:9 discriminator edge case

The current helpers generally decide that a room is wide when
`(adjustedUpper-adjustedLower) >= totalExtension`. The adjuster, however,
accepts an **original** span of only `totalExtension`, then removes that amount
from the span. Consequently an original span in
`[totalExtension, 2*totalExtension)` is widened but later helpers classify it
as narrow. An original `$0100` boss span works by accident in the 358 profile
(`$0100-$0070=$0090`, still at least `$0070`) but fails this discriminator in
the 398 profile (`$0100-$0090=$0070`, less than `$0090`). A dedicated marker or
entrance-aware logical-bound helper is safer than this post-transform test for
the boss fix.

## Recommended trace fields

For a deterministic good/bad comparison, capture these once per emulated
frame and on every allocation failure:

- level/entrance, frame, Layer1 X/Y, `$1B23/$1B25`;
- `$A0/$A2/$A4`, `$1E03-$1E0D`, `$EF/$F1`;
- record index, type, X/Y, initializer pointer, and `$192B` byte;
- allocator (`CODE_BDF3A2` or `CODE_BDF3C3`) and free raw indices;
- for type `$05`, parent and every derived child bookkeeping index;
- players plus actor IDs/positions/states/backlinks;
- K. Rool/controller `$1029,$130D,$1341,$1375,$145D,$1491,$152D`.

The companion `audit_object_windows.py` already reports the static frame
snapshot. A runtime recorder only needs to add the event history around it.
